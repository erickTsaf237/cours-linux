Piloter une machine sans écran, à l'autre bout du monde ou simplement dans ta VM, depuis le terminal de ton ordinateur : connexion chiffrée, clés à la place des mots de passe, copie de fichiers et serveur verrouillé.

    SSH : un terminal à distance

    SSH (Secure Shell) ouvre un shell sur une autre machine : tu tapes sur ton clavier, les commandes s'exécutent là-bas, et leur sortie revient dans ton terminal. Tout le trafic est chiffré, mot de passe compris. C'est ainsi qu'on administre la quasi-totalité des serveurs Linux.

    🖥️

    Le serveur : sshd

    Un service qui écoute sur le port 22. Paquet openssh-server, absent d'Ubuntu Desktop par défaut.

    💻

    Le client : ssh

    Déjà présent sur Linux, macOS et Windows 10/11 (PowerShell). Paquet openssh-client.

    user@ubuntu:~$ sudo apt install openssh-server
user@ubuntu:~$ systemctl status ssh --no-pager
○ ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/usr/lib/systemd/system/ssh.service; disabled; preset: enabled)
     Active: inactive (dead)
TriggeredBy: ● ssh.socket                         # c'est le socket qui écoute
user@ubuntu:~$ ss -tln | grep :22
LISTEN 0      4096         0.0.0.0:22        0.0.0.0:*
LISTEN 0      4096            [::]:22           [::]:*
user@ubuntu:~$ sudo ufw allow ssh                         # si le pare-feu est actif (module 12)
    « inactive (dead) » : est-ce grave ?

    Non. Depuis Ubuntu 22.10, SSH est activé à la demande : c'est ssh.socket (systemd, module 10) qui écoute le port 22 et ne démarre ssh.service qu'à la première connexion. ss -tln le confirme : le port 22 est bien ouvert.

    Se connecter à sa VM depuis Windows

    En mode NAT (module 12), la VM est invisible depuis ton ordinateur. On demande à VirtualBox de faire suivre un port de l'hôte vers le port 22 de la VM :

    1. Configuration › Réseau › Adaptateur 1

      Mode d'accès : NAT. Déplie Avancé, puis clique Redirection de ports.

    2. Ajouter une règle (+)

      Nom ssh, Protocole TCP, IP hôte 127.0.0.1, Port hôte 2222, IP invité vide, Port invité 22. OK.

    3. Se connecter depuis Windows

      Ouvre PowerShell (ou le Terminal Windows) et tape ssh -p 2222 user@localhost, avec ton nom d'utilisateur Ubuntu.

    PS C:\> ssh -p 2222 user@localhost
The authenticity of host '[localhost]:2222 ([127.0.0.1]:2222)' can't be established.
ED25519 key fingerprint is SHA256:mn3pUboINHWcHbUWUCfcU0I8D+mkMArhs9LzEtj14VU.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Warning: Permanently added '[localhost]:2222' (ED25519) to the list of known hosts.
user@localhost's password:                             # rien ne s'affiche en tapant : c'est normal
Welcome to Ubuntu 24.04 LTS (GNU/Linux 6.8.0-49-generic x86_64)
user@ubuntu:~$ exit                                    # ou Ctrl+D : retour à Windows
déconnexion
Connection to localhost closed.

    Avantages immédiats : copier-coller natif, terminal redimensionnable, et plus besoin de la fenêtre de la VM (tu peux la démarrer « sans affichage » : clic droit › Démarrer › Démarrage sans interface). En mode Accès par pont, pas de redirection : ssh user@192.168.1.37, avec l'adresse donnée par ip a dans la VM.

    L'empreinte du serveur : known_hosts

    À la première connexion, SSH note l'empreinte du serveur dans ~/.ssh/known_hosts. Si elle change ensuite, il refuse de se connecter :

    @@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Someone could be eavesdropping on you right now (man-in-the-middle attack)!
It is also possible that a host key has just been changed.
…
Host key verification failed.

    Si tu sais pourquoi (VM réinstallée, nouvelle VM sur le même port), efface l'ancienne empreinte puis reconnecte-toi : ssh-keygen -R "[localhost]:2222" (ou ssh-keygen -R 192.168.1.20). Si tu ne sais pas pourquoi, ne force rien : quelqu'un se fait peut-être passer pour ton serveur.

    Les clés SSH

    Une paire de clés remplace le mot de passe : la clé privée reste sur ton ordinateur, la clé publique est copiée sur chaque serveur. À la connexion, le serveur envoie un défi que seule la clé privée sait signer : aucun secret ne circule, et rien n'est devinable.

    user@ubuntu:~$ ssh-keygen -t ed25519 -C "user@portable"      # -C : un commentaire pour la reconnaître
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/user/.ssh/id_ed25519):       # Entrée : emplacement par défaut
Enter passphrase (empty for no passphrase):                        # une phrase de passe, recommandée
Enter same passphrase again:
Your identification has been saved in /home/user/.ssh/id_ed25519
Your public key has been saved in /home/user/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:mn3pUboINHWcHbUWUCfcU0I8D+mkMArhs9LzEtj14VU user@portable
user@ubuntu:~$ ls -l ~/.ssh
-rw------- 1 user user 411 nov.  17 09:55 id_ed25519          # privée : lisible par toi seul
-rw-r--r-- 1 user user  96 nov.  17 09:55 id_ed25519.pub      # publique : à distribuer
user@ubuntu:~$ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIPK3gdCsUsvo87U73ilPVssjUnnoe2lAp5f/gNZ9ivp5 user@portable

    Poser la clé publique sur le serveur

    Elle doit rejoindre ~/.ssh/authorized_keys de l'utilisateur, sur le serveur. Depuis Linux ou macOS, une commande s'en charge :

    user@ubuntu:~$ ssh-copy-id user@192.168.1.20
user@192.168.1.20's password:                          # le mot de passe, une dernière fois
Number of key(s) added: 1
user@ubuntu:~$ ssh user@192.168.1.20                   # plus de mot de passe demandé

    Windows n'a pas ssh-copy-id ; dans PowerShell, cette ligne fait le même travail (crée le dossier si besoin et ajoute la clé à la fin du fichier) :

    PS C:\> ssh-keygen -t ed25519
PS C:\> type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh -p 2222 user@localhost "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys"
    Les permissions comptent

    SSH ignore une clé que d'autres pourraient lire. Une clé privée trop ouverte donne :

    @         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
Permissions 0644 for '/home/user/.ssh/id_ed25519' are too open.
This private key will be ignored.

    Les bons réglages : chmod 700 ~/.ssh, chmod 600 ~/.ssh/id_ed25519 ~/.ssh/authorized_keys. Côté serveur, un dossier ~/.ssh ouvert à tous fait refuser la clé en silence : Permission denied (publickey,password).

    Phrase de passe sans la retaper : ssh-agent

    Une phrase de passe protège la clé si ton ordinateur est volé. Pour ne la taper qu'une fois par session, l'agent la garde en mémoire : sur Ubuntu Desktop il tourne déjà (ssh-add pour ajouter ta clé) ; sous Windows, active le service OpenSSH Authentication Agent puis ssh-add.

    Des raccourcis : ~/.ssh/config

    Taper ssh -p 2222 user@localhost à chaque fois devient vite lassant. Le fichier ~/.ssh/config de ton ordinateur (sous Windows : C:\Users\Nom\.ssh\config, sans extension) donne un surnom à chaque machine :

    Host vm
    HostName localhost
    Port 2222
    User user

Host serveur
    HostName 192.168.1.20
    User admin
    IdentityFile ~/.ssh/id_ed25519
    PS C:\> ssh vm                                   # remplace ssh -p 2222 user@localhost
PS C:\> ssh vm "df -h /"                           # exécuter une seule commande, puis revenir

    Le surnom marche aussi avec scp, rsync, et l'extension Remote - SSH de VS Code, qui ouvre les fichiers de la VM directement dans l'éditeur.

    Copier des fichiers : scp et rsync

    Les deux passent par le même tunnel chiffré. La syntaxe imite cp : source destination, où une machine distante s'écrit machine:chemin.

    user@ubuntu:~$ scp rapport.pdf vm:~/                       # envoyer un fichier dans le dossier personnel
user@ubuntu:~$ scp vm:/var/log/syslog .                    # récupérer un fichier ici (« . »)
user@ubuntu:~$ scp -r photos vm:~/                        # -r : un dossier entier
user@ubuntu:~$ rsync -av projet/ vm:~/projet/             # synchroniser : ne copie que ce qui a changé
sending incremental file list
created directory /home/user/projet
./
a.txt
sous/
sous/b.txt

sent 224 bytes  received 104 bytes  218.67 bytes/sec
total size is 4  speedup is 0.01
    📮

    scp

    Simple et partout disponible, y compris sous Windows. Recopie tout, à chaque fois.

    🔄

    rsync

    Ne transfère que les différences, reprend après une coupure, garde dates et droits (-a). Idéal pour les sauvegardes (module 15).

    rsync et la barre oblique finale

    rsync -av projet/ vm:~/copie/ copie le contenu de projet dans copie. rsync -av projet vm:~/copie/ (sans /) copie le dossier lui-même : on obtient copie/projet/…. Ajoute -n (dry run) pour voir ce qui se passerait sans rien copier. rsync doit être installé des deux côtés (c'est le cas sur Ubuntu).

    Sécuriser le serveur SSH

    Un serveur SSH ouvert sur Internet reçoit des milliers de tentatives de connexion par jour, de robots qui essaient des mots de passe courants. Trois réglages les rendent inutiles. Sur Ubuntu, on les écrit dans un fichier à part dans /etc/ssh/sshd_config.d/, plutôt que de modifier sshd_config : il survit aux mises à jour.

    PasswordAuthentication no      # clés uniquement
PermitRootLogin no             # on se connecte en utilisateur, puis sudo
AllowUsers user               # facultatif : seuls ces comptes peuvent entrer
    user@ubuntu:~$ sudo sshd -t                          # vérifie la syntaxe : silence = OK
user@ubuntu:~$ sudo systemctl restart ssh
user@ubuntu:~$ sudo sshd -T | grep -iE 'passwordauth|permitroot'   # la configuration réellement appliquée
permitrootlogin no
passwordauthentication no

    Une faute de frappe est signalée avant qu'elle ne fasse de dégâts :

    user@ubuntu:~$ sudo sshd -t
/etc/ssh/sshd_config.d/10-securite.conf: line 3: Bad configuration option: PasswordAuthentification
/etc/ssh/sshd_config.d/10-securite.conf: terminating, 1 bad configuration options
    Ne scie pas la branche sur laquelle tu es assis

    Avant de couper les mots de passe : vérifie que ta clé fonctionne (ssh vm sans mot de passe demandé). Après le redémarrage de ssh, garde ta session ouverte et teste dans un second terminal : en cas de problème, la première session te permet encore de corriger. Ensuite, un essai sans clé doit échouer : Permission denied (publickey).

    Et le port 22 ?

    Changer de port (Port 2200) réduit le bruit des robots dans les journaux, mais ne remplace pas les clés. Sur Ubuntu 24.04, le port est géré par le socket : après la modification, il faut sudo systemctl daemon-reload puis sudo systemctl restart ssh.socket, sans oublier sudo ufw allow 2200/tcp et la redirection de VirtualBox. Pour aller plus loin, sudo ufw limit ssh (module 12) freine les essais en rafale, et fail2ban bannit les adresses trop insistantes (module 19). Les tentatives se lisent avec journalctl -u ssh.

    Glossaire du module

    SSH
    Protocole de connexion chiffrée à distance (port 22).
    sshd
    Le serveur SSH (paquet openssh-server).
    Empreinte
    Identité du serveur, mémorisée dans ~/.ssh/known_hosts.
    Clé privée / publique
    Paire de clés : la privée reste chez toi, la publique va sur les serveurs.
    authorized_keys
    Liste des clés publiques autorisées pour un compte, sur le serveur.
    Phrase de passe
    Mot de passe qui chiffre la clé privée sur ton disque.
    ssh-agent
    Garde les clés déverrouillées en mémoire le temps d'une session.
    Redirection de port
    Fait suivre un port de l'hôte vers un port de la VM.
    scp / rsync
    Copie de fichiers par SSH / synchronisation différentielle.

    🧠 Quiz : as-tu tout retenu ?

    1. Quel paquet faut-il installer sur une machine pour pouvoir s'y connecter en SSH ?
    Le client sert à se connecter vers une machine ; le serveur à en accepter les connexions.
    2. Ta VM est en NAT avec une redirection 2222 → 22. Quelle commande lancer depuis Windows ?
    On se connecte au port 2222 de l'hôte, que VirtualBox fait suivre au port 22 de la VM.
    3. Quel fichier ne doit jamais quitter ton ordinateur ?
    C'est la clé privée ; la .pub se donne librement.
    4. Dans quel fichier du serveur la clé publique doit-elle se trouver ?
    ssh-copy-id l'y ajoute pour toi.
    5. SSH affiche « REMOTE HOST IDENTIFICATION HAS CHANGED » alors que rien n'a changé de ton côté. Que faire ?
    Une réinstallation l'explique ; sinon, c'est peut-être une usurpation. ssh-keygen -R seulement une fois rassuré.
    6. Que copie rsync -av photos/ vm:~/sauve/ ?
    La barre finale signifie « le contenu de ». -a inclut déjà la récursivité.
    7. Avant de passer PasswordAuthentication à no, il faut…
    Sinon, plus aucun moyen d'entrer : ni mot de passe, ni clé.
    8. Quelle commande vérifie la configuration de sshd sans rien redémarrer ?
    -t comme test : silencieuse si tout va bien.

    💬 Questions fréquentes

    Les questions qui reviennent le plus souvent sur ce module, avec leurs réponses.

    « Connection refused » : que vérifier ?

    Rien n'écoute à l'adresse et au port visés. Dans l'ordre : le serveur est-il installé (ss -tln | grep :22 dans la VM) ? La redirection de port de VirtualBox est-elle bien en TCP, 2222 → 22 ? Utilises-tu le bon port (-p 2222) ? Un « Connection timed out », lui, évoque plutôt un pare-feu qui ignore la demande, ou une mauvaise adresse.

    Le mot de passe ne s'affiche pas quand je le tape : le clavier est bloqué ?

    Non, c'est voulu : comme avec sudo, rien ne s'affiche, pas même des étoiles, pour ne pas révéler la longueur du mot de passe. Tape-le normalement et valide avec Entrée.

    Faut-il une paire de clés par serveur ?

    Non : une paire par ordinateur (ou par personne) suffit, et sa clé publique se pose sur autant de serveurs que tu veux. Si un ordinateur est perdu, il suffit de retirer sa ligne des authorized_keys : les autres continuent de fonctionner.
